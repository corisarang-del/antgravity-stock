# 일일 재무 데이터 자동 최신화 — 아키텍처 설계 및 계획

작성 시각: 2026-03-15

---

## 해결하고자 한 문제

현재 Pro 대시보드의 재무 데이터(fundamentals, history)는 **인메모리 TtlCache**만 사용.

- 서버 재시작 시 캐시 증발 → 첫 요청마다 dartlab/yfinance 실시간 호출
- dartlab은 DART API 호출 포함 → 응답 느림 (KR 종목 2~5초)
- 외부 API rate limit 위험 (특히 트래픽 증가 시)
- 매일 재무 데이터가 업데이트되지 않으면 Pro 유저가 stale 데이터를 볼 수 있음

---

## 해결된 것

### 아키텍처 설계 완료

**3계층 캐시 구조 확정:**

```
요청 → TtlCache(인메모리, 30min) hit?
  YES → 즉시 응답 (< 1ms)
  NO → Supabase financials_cache hit? (fetched_at < 25h)
    YES → TtlCache warm 후 응답 (< 50ms)
    NO → dartlab/yfinance 실시간 수집 → Supabase upsert + TtlCache set (2~5s)

GitHub Actions (매일 KST 06:00, UTC 21:00)
  → backend/scripts/daily_refresh.py
  → 16개 심볼 전체 dartlab + yfinance 수집
  → Supabase upsert (서버와 독립적으로 동작)

APScheduler (FastAPI 서버 내부)
  → 서버 시작 시: Supabase → TtlCache 워밍 (cold start 방지)
  → 매일 KST 07:00: 재워밍 (GitHub Actions 완료 후 1시간)
```

**기술 선택 근거:**

| 컴포넌트 | 선택 | 이유 |
|---------|------|------|
| 배치 실행 | GitHub Actions cron | 무료, 별도 서버 불필요, 실패 시 알림 내장 |
| 영속 저장 | Supabase JSONB | 이미 구축된 인프라, 추가 비용 없음 |
| 서버 스케줄러 | APScheduler AsyncIOScheduler | FastAPI asyncio 네이티브 통합 |
| 캐시 우선순위 | TtlCache > Supabase > 외부API | 응답 속도 최적화 |

## 기술적 결정 사항

| 결정 | 이유 |
|------|------|
| `fetched_at < 25h` 기준 (24h + 1h 버퍼) | GitHub Actions cron 지연 허용 (최대 ±30분) |
| RLS service_role만 허용 | 프론트엔드에서 재무 원시 데이터 직접 접근 차단 |
| 스크립트 독립 실행 | GitHub Actions runner에서 FastAPI 서버 없이 실행 가능해야 함 |
| `asyncio.sleep(1)` 심볼 간격 | dartlab DART API + yfinance rate limit 방지 |
| APScheduler KST 07:00 워밍 | GH Actions 완료 예상 시간(06:00~06:30) + 여유 30분 |
